# Smoke-test на отдельном тестовом окружении

## Что проверено при подготовке публичного пакета

Статически: шесть JSON разбираются; имена нод уникальны; межнодовые connections ссылаются на существующие ноды; подworkflow перечислены в карте; нет исходных credentials и активных workflow; public-файлы проверяются сканером.

**Это не end-to-end тест.** Runtime импортированной очищенной копии ещё не проверен. Демо записано на рабочем MVP, не на автоматически настроенном публичном шаблоне.

## Ручные проверки после настройки

Используйте вымышленные данные, отдельный бот и отдельную БД. Не сбрасывайте production-таблицы ради теста.

| Сценарий | Ожидаемое наблюдение |
| --- | --- |
| Новый клиент → запись | Запрошены имя/телефон, предложены слоты, получено подтверждение |
| Второй клиент выбирает уже занятый слот | Запись не дублируется; отображаются актуальные доступные слоты |
| Перенос / отмена | Обновлены статус/интервал и клиентские кнопки; сверить БД |
| Запрос менеджера | Менеджеру пришёл контекст, Reply доставлен нужному клиенту |
| Reply на уведомления двух клиентов | Не перепутаны lead/handoff и получатели |
| Кнопка менеджера от клиентского аккаунта | Не выполнено привилегированное действие |
| Старый или повторный callback | Не отправлен повторный согласованный follow-up |
| Напоминание | Подходящая будущая запись получила сообщение; сохранён sent timestamp |
| Результат встречи | Менеджер получил выбор, статус встречи изменился после решения |
| No-show → одобрить сообщение | Клиент получил отдельное сообщение, зафиксирован timestamp |
| AI follow-up | Сохранён черновик с версией, менеджеру доступны три действия |
| Отправить / отложить / закрыть | Отправка увеличивает счётчик; перенос меняет дату; закрытие прекращает цепочку |
| Ответ клиента / do-not-contact | Очищен ожидающий follow-up; отказ от контакта учитывается |
| Контролируемая ошибка в test workflow | Error Workflow получил событие, уведомление менеджеру не содержит секретов |
| Повторные/параллельные запуски | Проверены claims, конфликт слота и отсутствие нежелательных дублей |

Проверяйте не только зелёный execution: сопоставляйте Telegram-получателя, сохранённый статус, sent/claim-поля и историю.

## Остаточные риски

Сбой после фактической Telegram-отправки, но до обновления БД, может оставить неопределённость и привести к повторной попытке. Политика восстановления, конкурентные тесты и наблюдаемость должны быть проверены отдельно. AI-выход требует контроля содержания; наличие JSON-схемы не гарантирует фактическую точность текста.
